# v0.2 Design: Artifact-Grounded Office Work

Status: implemented public calibration release
Research cutoff: 2026-07-30
Release date: 2026-07-31
Release: `v0.2` Artifact Core
Long-term target: a stable public benchmark for ordinary knowledge-work
capability

## Implementation result

The 12-episode vertical slice described in this document is implemented under
`data/v0.2/`:

- 2 episodes in each of the 6 work modules;
- 48 Korean/English canonical/naturalistic request realizations;
- 20 hash-pinned inputs across PDF, DOCX, PPTX, XLSX, CSV, and TXT;
- 18 editable or machine-readable reference artifacts;
- all 8 workflow jobs represented;
- executable structure, file, source, package, and content checks;
- checked-in release validation and portable JSONL export.

All reference artifacts pass the deterministic release gates. The scenarios
are `calibration_ready`, while practitioner calibration is explicitly
`not_run`. Therefore the implemented release supports contract-conformance
experimentation, but not a global model ranking. The operational boundary and
commands are recorded in [V0.2-RELEASE.md](V0.2-RELEASE.md).

## Executive decision

`v0.2` should not add “PowerPoint” or “document design” as peers of the
existing 21 task intents. Those are artifact families and execution conditions,
not user intents.

Instead, `v0.2` should add a separate artifact-grounded suite in which a system
must turn a realistic workplace request and supplied files into a correct,
usable, editable deliverable. The existing controlled/naturalistic,
Korean/English pairing remains the project's differentiator.

The proposed root question is:

> Can a model or agent turn a realistic, sometimes incomplete workplace
> request and supplied files into a correct, usable, editable artifact, while
> making the right decision about whether to infer, clarify, revise, or hold?

The current 21 `primary_intent` values remain intact. New orthogonal axes
describe:

- the work operation, such as inspect, extract, create, revise, or validate;
- the input and output artifact families;
- the condition and trust level of attached files;
- the required interaction pattern;
- the authority and side-effect boundary;
- the evaluator needed to verify the result.

`v0.2` should ship the portable **Artifact Track** first. Stateful email,
calendar, CRM, and file-sharing actions belong in a later **Action Track**.
GUI-operation proficiency should be an optional adapter track, not silently
mixed into the artifact score.

  inspection, or checked-in project artifact.
- **Inferred**: a conclusion drawn from multiple verified observations.

## What “ordinary office-work capability” means

For this project, an ordinary office-work episode has all of these necessary
properties:

1. A horizontal workplace job, not primarily a coding exercise or a specialist
   licensing examination.
2. A realistic request that may be incomplete, conversational, or spread over
   several messages.
3. Bounded workplace context, often including one or more files.
4. A durable result: a usable artifact, a justified response, or a safe change
   in a controlled system.
5. Evaluation of the result, not merely whether a preferred tool sequence was
   followed.
6. Explicit treatment of uncertainty, permissions, and harmful or unnecessary
   changes.

Pure web question answering is not sufficient. Pure GUI clicking is not
sufficient. A beautiful deck with unsupported claims is not sufficient. A
correct spreadsheet that cannot be opened, audited, or edited is not
sufficient.

**Inferred:** a useful office-work benchmark must separate at least four
capability layers:

1. request understanding and interaction judgment;
2. file and source grounding;
3. work-product construction;
4. tool or environment execution.

## Benchmark research synthesis

### The benchmarks named in the initial research

|---|---|---|---|
| [GDPval](https://openai.com/index/gdpval/) | 1,320 expert-authored tasks across 44 occupations and 9 US industries; 220 gold tasks are open. Tasks include reference files and deliverables such as documents, slides, spreadsheets, diagrams, and multimedia. Expert graders blindly compare AI and human work. | Real work products, practitioner authorship, detailed task rubrics, and artifact-quality evaluation. | It is occupation-wide rather than focused on horizontal office-generalist work, is US/English centered, and its first version is one-shot and comparatively well specified. |

| [WorkBench](https://arxiv.org/abs/2405.00823) | 690 template-instantiated workplace tasks over 5 sandbox databases and 26 tools. | [WorkBench Revisited](https://arxiv.org/abs/2606.13715) | Re-audits the same benchmark two years later. | [GAIA](https://arxiv.org/abs/2311.12983) | 466 real-world questions requiring reasoning, multimodality, browsing, and tool use, with short unambiguous answers and three difficulty levels. | Good coverage of investigation, file handling, and tool-using robustness. | It primarily verifies an answer, not the functional, visual, or editorial quality of an office artifact. |
| [TheAgentCompany](https://arxiv.org/abs/2412.14161) | 175 tasks in a self-contained simulated software company, including browsing, programming, running tools, and communicating with coworkers, with execution and partial-credit evaluators. | Long-horizon organizational context and reproducible, self-hosted workplace state. | The software-company setting and coding component are too dominant for an ordinary office-work core. |
| [APEX-Agents](https://arxiv.org/abs/2601.14242) | 480 open tasks authored by investment-banking, consulting, and corporate-law professionals, with files, tools, rubrics, gold outputs, and a cross-application harness. | Strong task packages and professional-authored long-horizon work. | It represents high-end professional services, not the broad horizontal work of an ordinary office employee. |
| [Agents' Last Exam](https://arxiv.org/abs/2606.05405) | A living benchmark of 1,000+ verifiable, long-horizon tasks across 55 subfields and 13 industry clusters, created with 250+ experts and mapped to O*NET/SOC. | Living task pools, economic relevance, hidden verifiers, and broad professional coverage. | Its breadth, specialist difficulty, and environment cost are inappropriate as the initial office-generalist core. |

### Positioning conclusion

**Inferred:** none of the reviewed benchmarks owns this exact intersection:

- horizontal, ordinary office work;
- native file inputs and editable work products;
- controlled versus naturalistic request pairs;
- Korean and English coverage;
- clarification and revision judgment;
- portable artifact grading that does not require a full desktop VM.

That intersection is a credible position for RealWorld Prompt Kit. It is more
defensible than attempting to out-scale GDPval by occupation count or to
out-build OSWorld as a GUI environment.

## Jobs to be done

### For a benchmark user

> When I compare models or agent products for workplace use, help me discover
> which system can reliably turn the requests and files my colleagues actually
> provide into usable work products, so I can choose and deploy a system
> without relying on coding scores or polished demos.

### For a model or agent builder

> When an office workflow fails, help me distinguish request-understanding,
> file-grounding, work-product, interaction, and tool-execution failures, so I
> know what to improve.

### For a task contributor

> When I contribute a realistic work task, give me a bounded package, rights
> checklist, and verifiable rubric, so the task can be reviewed and reproduced
> without exposing company data.

### For a workplace adopter

> When I evaluate a candidate system, give me a capability and risk card rather
> than one opaque score, so I can match strengths and failure modes to my own
> workflows.

## v0.2 scope

### Track A: Artifact Core — in scope

The agent may use any declared tools, but is graded primarily on the delivered
files and response. No live external side effect is required.

Supported input families:

- PDF, including text-native and controlled scanned examples;
- DOCX;
- PPTX;
- XLSX and CSV;
- PNG and JPEG;
- mixed bundles containing several of the above;
- optional template, logo, image, font, or style-reference assets.

Supported output families:

- editable DOCX plus an optional PDF rendering;
- editable PPTX plus a PDF or image rendering;
- editable XLSX;
- PDF when it is explicitly a delivery format;
- a mixed output bundle with a manifest.

### Track B: Action Core — schema-ready, not scored in v0.2

Future tasks may update:

- email drafts and sends;
- calendar events;
- project or ticket records;
- CRM records;
- shared-drive files and permissions.

This track requires initial-state fixtures, final-state validators, authority
boundaries, reversible test environments, and separate collateral-damage
metrics. It should not be released until those controls exist.

### Explicitly out of scope for v0.2

- judging coding or terminal proficiency as the primary capability;
- sending real email or changing real third-party accounts;
- macro/VBA authoring or execution;
- measuring raw GUI clicking ability;
- video, audio, CAD, and 3D-production workflows;
- final legal, medical, tax, credit, employment, or other regulated decisions;
- claiming that synthetic examples represent empirical task frequency.

## Capability taxonomy

The suite should be organized by a primary **workflow job**, with artifact type
and office context recorded as independent axes.

### Workflow-job axis

1. `inspect`
2. `extract`
3. `synthesize`
4. `create`
5. `revise`
6. `repurpose`
7. `validate`
8. `package`

### Artifact-family axis

1. `response_only`
2. `pdf_or_image`
3. `document`
4. `presentation`
5. `spreadsheet`
6. `mixed_bundle`

### Input-condition axis

1. `clean`
2. `noisy_or_scanned`
3. `incomplete`
4. `conflicting`
5. `untrusted_embedded_content`

### Interaction axis

1. `one_shot`
2. `clarification_required`
3. `feedback_revision`
4. `scope_change`
5. `infeasible_or_hold`

Canonical and naturalistic request form is recorded on a separate
`request_forms` axis rather than being mixed into the interaction state.

### Authority axis

1. `read_only`
2. `draft_only`
3. `local_reversible_write`
4. `external_reversible_write`
5. `external_irreversible_action`

Only the first three authority levels are eligible for the `v0.2` Artifact
Track.

## v0.2 work modules and task backlog

These modules are reader-facing groupings. Every scenario still records exactly
one primary workflow job and one existing `primary_intent`.

### 1. Attached-file grounding

- Answer questions from a DOCX/PDF/PPTX/XLSX with page, slide, sheet, table, or
  cell-level evidence references where possible.
- Extract a table from a scanned PDF into a structured, reviewable form.
- Identify formulas, speaker notes, headers, hidden sheets, or other
  application-specific content relevant to the request.
- Compare two versions and report material differences.
- Reconcile conflicting figures across files without silently choosing one.
- Detect a missing, corrupt, irrelevant, or wrong-version attachment.
- Ignore instructions embedded inside an untrusted attachment when they
  conflict with the user's request.

### 2. Document work

- Turn notes and source files into an editable decision memo, report, SOP, or
  project brief.
- Fill and format an existing DOCX template without breaking its styles.
- Redesign a dense or inconsistent document for readability while preserving
  factual content.
- Revise a document against specific reviewer comments and report what changed.
- Create meeting minutes with decisions, owners, due dates, and unresolved
  questions from supplied notes.
- Export a delivery PDF while retaining the editable DOCX source.
- Apply a supplied brand/style reference without inventing missing brand rules.

### 3. Presentation work

- Turn a source bundle into an audience-specific presentation with a coherent
  narrative.
- Create an executive update deck from a report and workbook.
- Redesign an existing deck while preserving source-grounded claims.
- Revise selected slides from reviewer feedback without changing unrelated
  slides.
- Build or repair charts and tables so the visual encoding matches the data.
- Add useful speaker notes when requested.
- Produce an editable PPTX and a rendered preview with no clipping, overlap, or
  missing fonts.
- Adapt one source pack for different audiences without merely changing the
  title slide.

### 4. Spreadsheet work

- Clean and consolidate supplied CSV/XLSX data into a documented workbook.
- Build a multi-sheet workbook with formulas, assumptions, checks, and a
  summary view.
- Debug broken formulas, ranges, references, types, or charts.
- Create a decision-ready table or dashboard from raw data.
- Preserve formulas and editability instead of pasting unexplained values.
- Make a requested scoped change without overwriting unrelated cells,
  formatting, or hidden logic.
- Detect an impossible or under-specified calculation and request the decisive
  missing input.
- Produce a workbook that recalculates consistently in the reference office
  engine.

### 5. Cross-artifact workflow

- Turn meeting material into minutes, an action tracker, and a follow-up draft.
- Turn monthly operating data into a checked workbook, a management memo, and
  a short deck.
- Convert a long report into an executive deck while preserving an evidence
  trail back to the source.
- Merge a brief, template, data file, and image assets into a coherent delivery
  package.
- Keep names, dates, metrics, and recommendations consistent across all
  outputs.

### 6. Artifact quality control and delivery

- Audit a draft against its brief, sources, template, and output contract.
- Find unsupported claims, stale numbers, inconsistent labels, or broken
  references across files.
- Detect layout defects, truncated text, unreadable charts, and missing
  required sections.
- Fix only the requested scope and penalize unnecessary changes.
- Check accessibility-related properties that are deterministically
  inspectable, such as meaningful titles, reading order, and supplied alt
  text.
- Deliver the right files, names, formats, and folder structure with a concise
  completion note.

## Work-episode contract

The executable unit remains a semantic `scenario`, but a `v0.2` scenario must
package a complete work episode:

```text
request realizations
        +
versioned input assets
        +
interaction and authority contract
        +
required artifact contract
        +
task-specific evaluators
        =
reproducible office-work episode
```

Conceptual schema:

```yaml
schema: realworld-prompt-kit.scenario/0.2.0
scenario_id: rwpk.<intent>.<situation>.<number>

task:
  primary_intent: <one of the existing 21 values>
  workflow_job: create
  primary_domain: office_admin
  user_goal: {ko: "...", en: "..."}

assets:
  - asset_id: source_report
    path: assets/<scenario_id>/source-report.docx
    media_type: application/vnd.openxmlformats-officedocument.wordprocessingml.document
    attachment_role: authoritative_source
    trust_level: trusted
    locale_variant: ko-KR
    sha256: "..."
    rights_basis: original_project_authorship

realizations:
  - prompt_id: "..."
    locale: ko-KR
    form: naturalistic
    messages:
      - role: user
        content: "..."
        attachment_refs: [source_report]

artifact_contract:
  outputs:
    - artifact_id: executive_deck
      media_type: application/vnd.openxmlformats-officedocument.presentationml.presentation
      editable: true
      filename: executive-update-deck.pptx
  side_effect_scope: local_reversible_write

evaluation:
  hard_gates: [...]
  atomic_rubric_items: [...]
  human_calibration:
    required: true
    status: not_run
```

The schema should use asset references rather than putting binary content in
JSON. Every asset requires a hash, rights basis, privacy declaration, locale
status, and attachment role.

A harness must record which allowed delivery mode was used for an asset:

- the native file;
- a rendered image or PDF proxy;
- extracted text;
- an unsupported capability.

Silent conversion is prohibited because those modes test different
capabilities.

## Evaluation design

### 1. Non-compensable hard gates

A task cannot receive `full_pass` when any applicable hard gate fails:

- every required artifact is present;
- the file type and filename contract are satisfied;
- each file opens and parses in the reference environment;
- required editable structure is present;
- no critical source-grounding error is present;
- no forbidden external action occurred;
- no requested existing artifact was corrupted;
- no critical output is missing.

A beautiful but factually wrong deliverable cannot compensate for source
failure. A correct-looking PDF cannot compensate for a required but corrupt
PPTX. Safety cannot be averaged away by aesthetics.

### 2. Atomic task-specific rubric

Every soft or partial-credit item should:

- ask one binary or tightly bounded question;
- name its score dimension;
- point to the request or source evidence that justifies it;
- declare whether it is required, quality-improving, or a negative check;
- declare its scorer: deterministic, rule-assisted, model judge, or human;
- include an adjudication note for ambiguous cases.

Recommended dimensions:

1. `instruction_fulfillment`
2. `source_fidelity`
3. `functional_validity`
4. `audience_and_communication_fit`
5. `visual_and_layout_quality`
6. `editability_and_maintainability`
7. `interaction_judgment`
8. `scope_precision`

### 3. Triangulated graders

Use the smallest reliable grader for each criterion:

- deterministic file and OOXML inspection for structure, formulas, properties,
  names, required elements, and scoped changes;
- office-engine recalculation or rendering for formulas, pagination, clipping,
  and font/layout failures;
- source-grounded atomic model judgments for semantic criteria that cannot be
  reduced to a deterministic property;
- blind human review to calibrate and audit model judgments;
- pairwise preference only as a secondary presentation-quality signal.

Model judges must be versioned, operate one atomic criterion at a time, support
abstention, and be calibrated separately for Korean and English. A judge-only
score is not sufficient evidence for a stable leaderboard.

### 4. Multiple valid outputs

Do not compare whole files byte-for-byte with a single gold deliverable.
Golden files can aid authoring, debugging, and pairwise review, but final
grading should use required properties, task-specific criteria, and rendered
quality checks. This permits valid alternative structures without accepting
arbitrary output.

### 5. Report card, not one number

The default `v0.2` result should report:

- `full_pass_rate`
- `artifact_valid_rate`
- atomic score by rubric dimension
- score by work module and artifact family
- controlled/canonical score
- naturalistic score
- paired naturalistic robustness delta
- Korean score and English score
- locale parity gap, only on audited equivalent fixtures
- clarification/hold decision accuracy
- unnecessary-change rate
- unsupported-capability rate
- cost, latency, and tool-call count as descriptive metrics

No single aggregate leaderboard score should ship until human calibration
shows that the aggregation is stable and decision-useful. Even then, the
diagnostic scorecard must remain primary.

## Coverage and sampling

The artifact suite should cover combinations of:

- workflow job;
- artifact family;
- input condition;
- office context;
- interaction pattern;
- authority level;
- locale and prompt form;
- evaluator type.

Relevant office contexts for the first suite:

- meetings and project coordination;
- management and status reporting;
- basic finance and operations reporting;
- sales and marketing operations;
- HR and office administration;
- customer support and success;
- procurement and vendor coordination.

Do not build the full Cartesian product. Use pairwise coverage plus targeted
high-risk interactions, then review every scenario as a real work episode.

`CB8` remains the `v0.1` utterance-coverage primitive. Artifact coverage should
be represented by a new multidimensional coverage report rather than forcing
file formats into the existing prose/structured factor.

For a paired scenario:

- controlled and naturalistic requests within one locale use the identical
  asset version and artifact contract;
- Korean and English assets must be independently authored or equivalence
  audited, not mechanically translated and assumed equivalent;
- locale-specific scenarios are permitted, but must be excluded from paired
  locale-gap claims;
- translation, file-format conversion, and prompt paraphrase do not create new
  semantic breadth.

**Implemented calibration slice:** v0.2 contains 12 complete episodes. A future
reviewed candidate may target roughly 32–48 episodes, but that remains a cost
and learning budget rather than a coverage claim. The final reviewed count must
be an output of valid fixtures, reliable evaluators, and review evidence.

The public v0.2 files are marked `calibration_ready`, not `reviewed`. This
allows the complete harness and fixtures to be tested without implying that
automated conformance checks substitute for practitioner review.

## Authoring workflow

1. Collect a work-product archetype from a practitioner or documented public
   workflow.
2. Define the latent user goal before writing request text.
3. Create rights-cleared source files and a realistic initial state.
4. Define the output and authority contract.
5. Produce at least one expert reference deliverable.
6. Decompose quality into atomic rubric items tied to evidence.
7. Implement deterministic checks first.
8. Independently author controlled and naturalistic requests in each locale.
9. Run at least three materially different systems through the episode.
10. Blind-review outputs, repair the task or grader, and record evidence.
11. Freeze asset hashes, schema, grader versions, and reference renderings.

Task authors should not be allowed to mark their own task `reviewed` without a
second named reviewer.

## Lean validation plan

### Riskiest hypotheses

1. **Assumed:** native-file work reveals meaningful capability differences
   that the existing text-only scenarios do not.
2. **Assumed:** atomic hybrid graders can reproduce practitioner judgments in
   Korean and English well enough for comparative use.
3. **Assumed:** the controlled/naturalistic performance delta remains
   interpretable when outputs are complex artifacts.
4. **Unverified:** external teams will accept a portable artifact harness as a
   useful intermediate step before a full office sandbox.

### Vertical-slice experiment

Build 12 episodes spanning attached-file grounding, documents, presentations,
spreadsheets, cross-artifact work, and quality control. Run four prompt
realizations per episode against at least three systems with different tool
stacks.

Use two independent workplace reviewers per sampled output, blind to system
identity. Before public model comparison:

- the same artifact must receive identical deterministic hard-gate results in
  each supported reference environment;
- every hard gate must have an unambiguous, executable test;
- unresolved reviewer disagreement must lead to rubric repair or item removal;
- system ordering must not reverse merely by removing one model judge from an
  ensemble;
- Korean and English judge behavior must be calibrated separately;
- at least one episode per module must distinguish the pilot systems rather
  than producing an all-pass or all-fail result;
- a second team must be able to run the package without author assistance.

If these conditions fail, `v0.2` remains a calibration release and must not
claim leaderboard validity.

## Failure-mode analysis

| Failure mode | Effect | Early indicator | Required control |
|---|---|---|---|
| The project still measures prompt text but markets office capability. | Invalid construct claim. | No native files or durable outputs in scored tasks. | Require complete work episodes and artifact hard gates. |
| A model judge rewards fluent or attractive hallucinations. | Wrong systems rank highly. | High judge score with source-fidelity failures. | Atomic source-linked criteria, deterministic checks, blind human calibration. |
| GUI difficulty overwhelms work quality. | Score becomes an app-control benchmark. | Correct artifacts differ sharply by screen or app version. | Separate Artifact and GUI/Action tracks. |
| Exact gold-file comparison rejects valid alternatives. | False failures and author-style overfitting. | Human reviewers accept outputs that the grader rejects. | Property checks and task-specific rubrics. |
| Successful completion hides harmful or unnecessary changes. | Unsafe agents appear capable. | Wrong recipients, overwritten cells, or unrelated slide edits. | Non-compensable side-effect and scope-precision checks. |
| Public tasks become training data. | Leaderboard inflation. | Rapid saturation without product evidence. | Frozen public core plus sealed, rotating challenge sets by the stable release. |
| Korean is a translated shadow of English. | Misleading bilingual claim. | Korean-only layout, typography, honorific, or parsing failures. | Native authoring, localized assets, locale-specific calibration and reporting. |
| Synthetic volume outruns human review. | Large but low-validity suite. | Most tasks remain `draft` or share templated rubrics. | Full review requirement and no scenario-count target as a quality proxy. |
| Artifact runner is too difficult to install. | Low adoption and irreproducible scores. | Only the authors can run it. | Portable fixtures, reference CLI, conformance tests, optional containers. |
| A static benchmark saturates. | Score no longer discriminates systems. | Ceiling performance, as seen in the WorkBench revisit. | Stable core, versioned challenge pool, scheduled audit and retirement policy. |

- attached native files;

### Stable office capability benchmark

The stable release should ship only when:

- artifact, interaction, and action tracks have explicit boundaries;
- every public task has traceable provenance and named review evidence;
- hidden evaluation can be reproduced by an independent operator;
- deterministic and model-assisted graders have published human calibration;
- Korean and English have independent validity evidence;
- benchmark reports remain diagnostic rather than only publishing an Elo;
- the stable core is versioned separately from rotating challenge tasks;
- unsupported capability, model failure, harness failure, and grader failure are
  distinguishable in result records.

## Material assumptions and open research

1. **Unverified market assumption:** Korean/English naturalistic office-work
   evaluation is a sufficiently important gap to drive adoption. Validate with
   task diaries, user interviews, and external pilot partners.
2. **Assumed scope choice:** a portable artifact track provides more learning
   per unit of implementation cost than building a full office VM in `v0.2`.
3. **Assumed evaluation choice:** hybrid atomic grading can be reliable enough
   if deterministic checks and human calibration constrain model judges.

The highest-value next evidence is not another large synthetic generation run.
It is a small end-to-end pilot with real files, expert rubrics, multiple agent
stacks, and blinded human review.
